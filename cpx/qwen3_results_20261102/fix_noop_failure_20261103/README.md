# 规则更新：重复无效动作达到阈值即判失败（2026-11-03）

本目录记录对 `qwen3_8b_a11y_pair_20261101_full_v2` 的**规则修订与回放重算**。不是新实验，原始 `records/` 与 `computed_summary.json` 保持不变；本目录的 `metrics.json` 是同一批原始 episode 在新规则下的重算结果。

## 1. 规则变化

旧口径：重复无效动作只是“停”，最终是否成功仍由任务评估器看最终屏幕状态决定。`RecipeDeleteMultipleRecipesWithConstraint` 因此出现 **40 次调用、`done=false`、`success=1`** 的异常记录。

新口径：

> 连续 **5 次完全相同的动作**，且执行后页面状态不变 → 该 episode **直接判失败**，立即结束，不再执行后续动作。

- 阈值可用环境变量 `AW_NOOP_STOP` 覆盖（默认 5，最小 2）。
- 生效范围：所有 arm（BASE / FULL45 都走同一循环），与图、探索、hard 模式无关。
- 判失败方式：`is_successful = 0`，并写 `stuck_failed = true`；不伪装成基础设施错误。

## 2. 代码改动

patch：`stuck_loop_guard.patch`（对部署源码 `qwen3_a11y_20261101` 的 `experiments/trace_reachability_validation/scripts/full_run.py` 应用）。

| 文件 | 改动 |
|---|---|
| `noop_guard.py`（新增） | `NoopGuard`：累计“相同动作 + 页面未变”的连续次数，到阈值返回一次 `True` |
| `full_run.py` | ① import；② 循环前初始化；③ 每步比较上一动作与当前页面，触发时写 `noop_stop` 行并 `break`；④ `_run()` 里把 `m_noop_stop` 的 episode 强制 `is_successful=0.0`、`stuck_failed=true` |
| `test_noop_guard.py`（新增） | 5 个纯逻辑测试，含用本任务 9–40 步回放的触发测试 |
| `replay_guard.py`（新增） | 对归档 episode 逐动作回放，估计新规则下的触发与调用数 |

判定的“页面未变”沿用 runtime 的 `R.same_state`（`exact_sig` + `content_sig`），不是截图 pHash。

## 3. 回放方法与边界

- 数据：`formal_logs.tar.gz` 中全部 232 个 episode 的 `steps.jsonl` 与 `a11y/*.json.gz`。
- 对每个 model 动作，比较动作前快照与下一步快照（解压后字节相等即视为未变），复现 `NoopGuard`。
- 触发时，`model_calls` = 触发前已执行的 model 行数 + 这些行里的 `requery` 次数。
- **字节相等比 `same_state` 更严格**：若页面只有状态栏时间等无关差异，回放可能漏判触发。因此本结果对“失败”是保守估计（不会多判失败）。
- 本目录数字是**重算**，不是复跑；复跑会因采样/等待/页面稳定时机略有差异。

## 4. 新规则下的结果

| 口径 | 方法 | 成功率 | 平均调用数* | 成功题调用数 | 共同成功调用数 |
|---|---|---:|---:|---:|---|
| 全部 116 | BASE | 13.79%（16/116） | 11.16 | 6.50† | — |
| 全部 116 | FULL45 | **17.24%（20/116）** | 9.50 | 6.75† | 12 道：**6.92 vs 6.25（−9.6%）** |

† “成功题调用数”是各 arm **自己成功集**的均值（BASE 16 题、FULL45 20 题），题集不同，**不能横向比较**；配对口径只看“共同成功”这一列。

对照旧口径：

| | 旧规则 | 新规则 |
|---|---:|---:|
| BASE 成功率 | 13.79%（16/116） | 13.79%（16/116） |
| FULL45 成功率 | 18.10%（21/116） | **17.24%（20/116）** |
| 成功率差 | +4.31 pt | **+3.45 pt** |
| 共同成功 | 13 道：6.77 vs 8.85（+30.7%） | **12 道：6.92 vs 6.25（−9.6%）** |

- 唯一从成功变成失败的是 `RecipeDeleteMultipleRecipesWithConstraint`：40 次调用 → 14 次触发（原 `+30.7%` 全部来自这一题）。
- 触发统计：BASE 23 个 episode、FULL45 28 个 episode；其中原本就失败的分别为 23 和 27，只有 1 个原本成功。
- 平均调用数下降（BASE 14.71→11.16，FULL45 12.89→9.50）主要是因为大量**本来就失败**的 episode 提前结束，不代表成功轨迹加速。成功题调用数只在 FULL45 上因移除那题从 8.33 变为 6.75。
- * 平均调用数包含提前终止的失败题，不能当作端到端加速结论。

## 5. 结论

- 修掉死循环后，**FULL45 仍多成功 4 题（+3.45 pt）**，但共同成功 12 题上的调用数 **FULL45 少 9.6%**（6.92→6.25），不再是原来的 +30.7%。
- 这个 −9.6% 是“新规则下两边都成功、且都没有触发阈值”的配对口径，不再是事后删题；但它只有 12 题，仍不宜过度解读。
- 旧归档的 18.10% / +30.7% 保留为“旧规则”记录，不与本表混用。
